# CSC-121 course brief

This is the durable teaching contract for the Starter. Revise it deliberately
when the audience, outcomes, evidence, or course format changes.

## Audience

Undergraduate learners with no assumed programming experience. They should be
comfortable using a web browser and managing ordinary files, but the course
must teach every programming tool explicitly. Do not make terminal, Git, or
GitHub fluency a prerequisite for learning the first Python concepts.

Do not design around an imaginary average learner. Begin with Thonny's focused
editor-and-run loop, build recovery paths for file-management problems, and
offer optional depth to students who have programmed before.

## Promise

Students will be able to turn a small real-world problem into a readable,
tested Python program and explain how their solution works.

## Entry requirements

- A computer capable of running [Thonny](https://thonny.org/), or an approved
  equivalent beginner Python environment.
- A web browser for the PathMX course website and institution LMS.
- No prior Python, terminal, Git, GitHub, or AI-agent experience.
- Access to the institution's ordinary LMS or communication channel.

A GitHub account and Codespaces access are later-course requirements. The
instructor must announce and test them before the applied-project unit rather
than requiring them on the first day.

## Mode and pace

Facilitated, 15-week course that moves from explicit skills practice into
project-based learning:

- two lecture or workshop meetings each week;
- one guided lab;
- one independent application or project checkpoint;
- approximately four to seven hours of work outside meetings, adjusted to the
  institution's credit-hour policy.

## Capability outcomes and evidence

| Capability | Observable evidence |
| --- | --- |
| Decompose a problem | A short plan that becomes small working increments |
| Use Python fundamentals | Programs using values, decisions, repetition, functions, and structured data appropriately |
| Work with external data and code | A program that reads data and uses a documented module or package |
| Test and debug | Reproducible examples and an explanation of a repaired defect |
| Use source control | A later project repository with frequent descriptive commits |
| Communicate about code | README, code explanation, feedback response, and live demonstration |
| Build independently | A final project that runs, serves a stated user or purpose, and can be explained by its author |

## Final performance

Each student proposes and completes one project in a suitable introductory
scope. The repository must contain:

- a project specification and explicit non-goals;
- a working program;
- an incremental commit history;
- tests or a repeatable manual verification plan;
- a README that another person can follow;
- a short reflection about decisions, problems, and assistance used.

Students demonstrate the project and answer questions about its behavior and
their own code.

## Feedback and assessment

Use four recurring evidence categories:

- **Projects:** independent application and transfer.
- **Paper exams:** unaided code reading, tracing, writing, and explanation.
- **Practice:** labs, checkpoints, and supported attempts.
- **Professional practice:** attendance or participation as permitted by local
  policy, source control, communication, revision, and the ability to explain
  submitted work.

The included syllabus offers an editable starting point. Its exact weights are
not part of the technical course contract.

## Tool progression

1. **Foundations:** PathMX is the course website. Students type, run, and debug
   small files in Thonny and submit them through the simplest approved channel,
   normally the LMS.
2. **Applied projects:** teach VS Code in GitHub Codespaces and the small Git
   loop students actually need. Treat setup and recovery as course content.
3. **Final project:** use repository history, review, and optional bounded agent
   workflows to support a more industry-shaped project.

Typing examples and solutions manually is deliberate practice. Like scales in
music or repeated physical training, it builds coordination between reading a
program, producing syntax, predicting behavior, and noticing errors. The goal
is fluency, not busywork; keep each exercise small enough that the repetition
serves a named capability.

## AI boundary

The course moves through three stages:

1. In Unit 1, student use of generative AI is not permitted. Students build
   initial fluency by typing, tracing, running, and revising code themselves.
2. In Unit 2, AI remains unavailable unless the instructor explicitly opens a
   bounded use after students have demonstrated the relevant foundation. Any
   permitted material use must be recorded.
3. In Unit 3, the instructor may teach coding agents for bounded project work.
   Students remain responsible for central decisions and must understand all
   submitted code.

Instructor use of an agent to maintain the course or prepare feedback does not
change student permissions. The instructor reviews its output and owns every
curriculum, feedback, integrity, and grading decision.

The policy must apply to the capability, not one vendor or model name.

## Distribution

- PathMX is the learner-facing course website and reference surface.
- The LMS distributes and collects early Python files and remains the official
  record system.
- GitHub and Codespaces hold later applied and final project work.
- Repository assignment creation is an optional later operational layer:
  Classroom 50 or ordinary GitHub may be piloted without changing curriculum.
- The institution's LMS remains the authority for official grades, enrollment,
  accommodations, and required records unless the instructor establishes a
  different approved system.

## Privacy

The reusable repository contains no real learners or term records. A private
term repository or approved institutional system must own rosters,
submissions, grades, accommodation information, and private feedback.
