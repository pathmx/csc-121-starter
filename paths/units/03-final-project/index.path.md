# Unit 3: Final project studio

Design, build, test, document, and present one project that serves a clear
person or purpose.

## Unit destination

You will demonstrate that you can make and explain a sequence of programming
decisions—not merely produce a large amount of code.

## Scope contract

A suitable project has:

- one named user or use situation;
- one central capability that can be demonstrated end to end;
- a Python core the student can explain;
- a small number of supporting features;
- explicit non-goals;
- a path to a working first slice in one week.

Possible forms include a command-line tool, small data application, simple web
application, or small game/simulation. A project should not require a mobile
app store, production payments, sensitive personal data, or an unbounded AI
system to count as complete.

---

## Week 11: Proposal and scaffold

**Questions:** Who is it for? What problem or experience does it address? What
will a person be able to demonstrate at the end? What is explicitly out of
scope?

**Evidence:**

- completed `project.spec.md`;
- repository created from the final-project template;
- environment runs from the README;
- one placeholder-to-output path works;
- first journal entry and initial commits.

An instructor approves or narrows the scope before implementation expands.

---

## Week 12: First complete slice

Build the smallest end-to-end user flow. Prefer one complete thin slice over
several disconnected subsystems.

**Evidence:** a person can provide one input or action and observe one useful
result. The student can identify the central logic and demonstrate a normal
case.

**Checkpoint conversation:** What works now? What evidence proves it? What is
the most important risk? What will be deliberately deferred?

---

## Week 13: Minimum viable project

Complete the central experience, handle the most likely failure, and remove or
defer features that threaten the core.

**Evidence:** a stable demonstration from a clean start, plus a journal entry
that distinguishes complete, partial, and deferred work.

---

## Week 14: Test, revise, and document

- test normal, boundary, and failure cases;
- repair the highest-impact problem;
- make setup reproducible;
- explain project structure and important decisions in the README;
- acknowledge material human and AI assistance;
- prepare a release candidate.

**Peer review:** another student follows the README without oral rescue and
reports where the process or behavior differs from the documentation.

---

## Week 15: Demo and explanation

The final evidence includes:

- a working repository at the submitted revision;
- a concise demonstration centered on the intended user;
- an explanation of one important algorithm or transformation;
- an explanation of one bug, test, or revision;
- a reflection on scope, assistance, and what should happen next.

The instructor should assess the known submitted revision, not an unrecorded
last-minute local state.

## Agent boundary

Coding agents may help with planning, debugging, tests, setup, documentation,
front-end work, and unfamiliar libraries when permitted. The student owns the
problem definition, scope, central behavior, verification, and explanation.
See [responsible agent use](../../resources/agent-use.policy.md).

## Before teaching this unit

This unit is mapped, not pilot-ready. The instructor must publish the rubric,
checkpoint dates, project categories, demonstration constraints, deployment
expectations, and exact AI-use disclosure before proposals begin.
